# To CoT or not to CoT? Chain-of-Thought Helps Mainly on Math and Symbolic Reasoning

## 一句话概括

这篇 ICLR 2025 论文的核心结论是：**CoT 不是一种普遍有效的“先思考再回答”策略。它主要在需要数学计算、形式逻辑和符号状态跟踪的任务上有效；在常识判断、知识问答、阅读理解和其他软推理任务上，收益通常很小，甚至可能降低性能。**

## 论文研究的问题

Chain-of-Thought（CoT）已经成为大语言模型处理“推理任务”时的常用策略，但作者质疑一个被广泛接受的假设：只要任务需要推理，让模型先输出思维链就应该比直接回答更准确。

论文主要回答两个问题：

1. CoT 究竟在哪些类型的任务上有效？
2. CoT 的收益来自问题规划，还是来自对中间计算步骤的执行？

## 研究方法

作者使用了两类互相补充的证据。

### 1. 文献元分析

- 检索 ICLR 2024、EACL 2024 和 NAACL 2024 的 4642 篇论文。
- 找到 110 篇直接比较 CoT 与 Direct Answer 的论文。
- 提取出 1218 组“模型 × 任务”实验比较。
- 将任务重新划分为数学、符号与算法推理、逻辑推理、常识、知识、阅读理解等类别。

### 2. 统一控制实验

- 覆盖 14 个不同系列和规模的语言模型。
- 覆盖 20 个数据集。
- 同时测试 zero-shot 和 few-shot 设置。
- 比较 Direct Answer prompt 与 CoT prompt。
- 使用 greedy decoding，并针对每个模型和数据集设计答案解析器，以降低格式失败对准确率的干扰。

## 发现一：CoT 的收益主要集中在符号任务

文献元分析中的平均提升如下：

| 任务类型 | CoT 平均提升 |
| --- | ---: |
| 符号和算法推理 | +14.2 个百分点 |
| 数学推理 | +12.3 个百分点 |
| 逻辑推理 | +6.9 个百分点 |
| 其他任务整体 | 约 +0.7 个百分点 |

作者自己的实验也得到相同趋势：

- MATH、GSM8K 等数学任务提升最大。
- ContextHub 等形式逻辑任务明显受益。
- CommonsenseQA、PIQA、Social IQa、WinoGrande、ARC 和部分 LSAT 任务基本没有稳定收益。
- MuSiQue 虽然要求多跳推理，但 CoT 没有带来整体提升。
- 对长文本自由生成任务 BiGGen Bench，先规划再回答也只有轻微收益。

因此，**“任务需要多步推理”并不足以预测 CoT 是否有效**。真正重要的是这些步骤是否涉及可执行的计算、符号变换或中间状态跟踪。

## MMLU 为什么看起来受益

MMLU 混合了数学、知识和其他学科，因此整体分数可能掩盖不同问题类型之间的差异。

作者发现，一个非常简单的特征就能定位大部分收益：问题或模型生成的 CoT 中是否包含等号 `=`。包含 `=` 通常意味着模型正在执行方程、数值计算或符号操作。

虽然这类样本只占 MMLU 的一小部分，但在部分模型上，它们解释了约 95% 的整体 CoT 收益。去掉这些数学相关样本后，CoT 与 Direct Answer 的准确率基本接近。

这说明 MMLU 上的整体提升不能被解释为“CoT 改善了所有知识推理”，它主要是由数学和符号问题带来的。

## 发现二：CoT 主要帮助执行，而不是规划

作者把符号推理拆成两个阶段：

1. **Planning**：把自然语言问题转换成方程、Python 程序或逻辑规则。
2. **Execution**：逐步执行这些规则，跟踪中间计算，最终得到答案。

实验比较了五种方法：

- Direct Answer
- 普通 CoT
- 先生成形式化计划，再直接回答
- 先生成形式化计划，再用 CoT 执行
- 先生成形式化计划，再交给 Python 或 Z3 求解器执行

结果显示：

- 仅仅生成计划通常不够，`Plan + Direct` 的提升很小。
- CoT 的主要作用是帮助模型逐步执行计算并保存中间状态。
- 外部 Python 或 Z3 求解器在大多数设置中又明显超过 CoT。

因此，作者把 CoT 看作一种**通用但不够可靠的符号求解器近似**：它比让模型直接心算更好，但当问题能够接入真正的计算器、程序解释器或逻辑求解器时，工具通常更加准确。

## 论文并不是说 CoT 完全没用

论文反对的是“所有推理任务都默认使用 CoT”，而不是完全否定 CoT：

- 数学计算、形式逻辑、算法模拟和实体状态跟踪适合使用 CoT。
- 常识判断、语义评价、知识检索和阅读理解不一定需要 CoT。
- 如果任务可以形式化，工具调用往往优于纯语言 CoT。
- 如果只需要最终标签，可以选择性启用 CoT，以降低 token 和推理成本。
- 如果需要人类可读的解释，CoT 仍可能有价值，但解释价值与答案准确率是两个不同目标。

## 对科学写作评价实验的意义

Actionability、Helpfulness、Verifiability、Coherence 等科学写作评价主要属于**软语义判断**，而不是数学计算或可执行的符号推理。因此，这篇论文与你当前实验结果具有较强的一致性：

- Label-only SFT 已经能够直接学习评分边界。
- 生成较长的 reasoning 不一定提供新的决策信息。
- CoT 可能引入额外语言噪声，暴露错误的中间判断，并增加输出成本。
- Paper Align 可以让一个模型兼容 Direct 和 Reason 两种模式，但不一定提高最终标签准确率。
- 如果需要解释，应当把 rationale 的正确性、相关性和忠实性作为独立目标评价，而不能假设 rationale 会自动提高评分性能。

不过，两项研究仍需严格区分：本文主要研究 **inference-time prompting**，而你的实验还研究 **rationale supervision/SFT**。这篇论文能够支持“科学写作评价不属于 CoT 的优势任务”这一解释，但不能单独证明 CoT SFT 为什么会导致性能退化。

## 论文的局限

- 重点研究 prompt-based CoT，没有覆盖当前专门训练的 reasoning model。
- 对任务类型的分类存在一定主观性。
- `=` 特征有时需要查看已经生成的 CoT，不能完全用于生成前的低成本路由。
- 文献元分析可能受到发表偏差影响。
- 没有充分覆盖长周期规划任务。
- 不同模型可能接触过测试数据，存在数据污染风险。
- CoT 与 Direct Answer 没有严格匹配推理计算量；Direct Answer 使用同等计算预算进行多次采样或集成后，比较结果可能变化。
- 工具增强并非在每个任务上都更好；如果模型生成的程序或逻辑表达式无法解析，工具方法也会失败。

## 总结

CoT 更像是给语言模型增加了一块外显的计算草稿纸。只有当任务确实需要在草稿纸上持续计算和跟踪符号状态时，它才会稳定发挥作用；对于科学写作评价这类软语义判断，输出更长的推理过程并不意味着判断会更准确。

论文给出的实践建议不是“永远不用 CoT”，而是：**根据任务的计算结构选择性使用 CoT，并把答案准确率、解释质量与计算成本作为彼此独立的评价维度。**
